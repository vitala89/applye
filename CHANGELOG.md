# Changelog

All notable changes to Applye are documented here.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).
Applye is pre-1.0, so it follows `0.x` versioning: while on `0.x`, the minor
number covers new capability and the patch number covers fixes and release
plumbing. The version in `package.json`, `Cargo.toml`, and `tauri.conf.json`
is the single source of truth; this file tracks what changed at each tag.

## [Unreleased]

### Security

- **The second wave of dependency advisories is closed, and none of it ever shipped.** Nine Dependabot alerts opened against `undici`, plus seven more that only `npm audit` reported - the audit found 16 where Dependabot found 9. All of them are development scope: `undici` reaches the tree through `@angular/build` and through `node-gyp` under `@angular/cli`, `hono` and `brace-expansion` the same way. `npm audit --omit=dev` read 0 before the fix and reads 0 after it, so nothing vulnerable was ever in the Tauri bundle or the web build. Every fix is a patch-level bump forced through `overrides`, because `@angular/build` pins `undici` to the exact string `7.28.0` and npm's own suggested remedy was a semver-major **downgrade** of `@angular/build`. `undici` goes to 6.28.0 and 7.29.0, `hono` to 4.13.0, and the three existing `brace-expansion` pins move up within their own majors to 1.1.18, 2.1.4 and 5.0.9 - keyed by major, which is what keeps the earlier refusal intact: forcing every copy to 5.x breaks the `minimatch` 3.1.5 callers and no gate catches it, so the 1.x copies were left on 1.x and checked by hand to still export a callable. `npm audit` now reports 0 vulnerabilities. The one remaining alert, `glib` RUSTSEC-2024-0429, is unchanged and still not fixable here - the gtk-rs 0.18 stack reaches it through the `gtk` version Tauri pins, it is Linux-only, and it is deliberately left open rather than dismissed so that it is what tells us Tauri has moved.

### Fixed

- **A key check that answered for the wrong provider could unlock the wizard.** Onboarding asks the OS keyring whether the selected provider already has a key, and that lookup is asynchronous. Switching provider while it was in flight let the answer for the provider you left land on the one you had moved to - so a provider with no key could report as connected, and Continue unlocked on a key that was not there. The guard against this existed but nothing tested it: removing it left all 1224 tests green. It is now covered, along with the key-format check and the path where the keyring write fails.

### Added

- **A check that proves a stylesheet split did not drop anything.** Splitting a page into child components moves CSS between files, and until now that move was verified by comparing which selectors existed before and after. That check cannot fail the way it needs to: a selector can survive with its declarations gone. It did. During the Discover Sources drawer extraction the shared `.dv-input, .dv-select` rule was split so the child kept only `.dv-select` and the page kept `.dv-input,` as a selector with no body - which Sass silently attached to the rule that followed it. Three inputs rendered with browser defaults and the page's filter field inherited a 60vh centred empty-state layout, and type-check, lint, 1224 unit tests and the Angular build all passed on it. `npm run quality:style-move -- --base main <files>` compiles both sides of the split and compares **declarations** per selector, reporting what was lost and what was gained. Run against the broken tree it names `.dv-input` and all eight declarations; against the fixed tree it reports lossless. It is not part of `npm run quality`, because it needs the specific files of the split under review.

- **Profile's shared styles are defined once, and the partial is scoped to the page.** Profile is a header, a target-roles card, a photo card, a five-section editor and an AI-tools card in one 733-line stylesheet, and its five editor sections are the next cuts. Measured from the template: of the 95 classes it uses, 30 appear in more than one block. Template **742 -> 628**, class **897 -> 797**, stylesheet **766 -> 718**; across both cuts the wizard is down from 878/1002/1045. Nothing renders or behaves differently.

So the state moved into a service the wizard provides and the card mutates, rather than being passed down and evented back up, which would have split the save flow across the boundary. That is the arrangement the Discover Sources drawer already uses. Eight more classes - the panel shell and the numbered step list, shared by both panels - joined the wizard's global partial first. Template **878 -> 742**, class **1002 -> 897**, stylesheet **894 -> 766**; all three were over budget before and remain so. Nothing renders or behaves differently.

- **The cover-letter editor's five text blocks are one component.** Date, subject, greeting, closing and signature each rendered a collapsible section around one text field. Normalising the block key out of the markup showed subject, greeting, closing and signature to be **identical, line for line**, and date to be the same thing without a Regenerate button - 308 template lines that were one component written five times. They are now `cover-letter-block`, rendered five times, and the proof it is faithful runs the other way: substituting each key back into the component reproduces all five original blocks exactly. The three action classes the page still needs for its recipient and body blocks moved to a partial emitted once from `styles.scss`, and the word-count rules became pure functions with their own tests. A consumer audit found the drawer the cleanest seam available: of the twenty-five symbols its markup names, **twenty-three are used nowhere else on the page**. The list itself moves to `DiscoverSourcesService`, which the page provides, because both sides genuinely read it - the page scans over the enabled sources and counts them, the drawer adds, removes and switches them. Passing it down and eventing back up would have stranded the drawer's optimistic toggle, which flips a row before the write lands so the checkbox does not lag the click, on the wrong side of the boundary. Stylesheet **1915 -> 1466**, template **1070 -> 808**, class **1069 -> 890**; all three are still over budget. No behaviour changed.

- **Discover's button, icon button, text input and overlay are defined once.** Extracting the drawer would have duplicated them, because style encapsulation stops the page's stylesheet at a child component's boundary. - **The onboarding wizard's shared styles are defined once.** The wizard is six step blocks in one 1045-line stylesheet, and the steps are being extracted into their own components. Angular scopes a component's compiled CSS, so a class defined on the page does not reach a child extracted out of it - which means every one of those five later cuts would have had to decide again what to do with the same shared classes, and the last cut that made that decision under time pressure lost a rule. Measured from the template instead: of the 130 classes it uses, exactly 14 appear in more than one step - the heading set, the card and badge primitives, the form primitives, and the spinner and key-status pieces the AI-setup and resume steps share. Those move into `_onboarding-shell.scss`, emitted once from `styles.scss`, the same arrangement `_editor-shell.scss` already uses for the document editors. The page's stylesheet goes **1045 -> 894** lines with no other change, and the remaining five cuts become mechanical. Nothing renders differently: the page's stylesheet no longer mentions a single hoisted class, so no specificity or ordering interaction is possible, and `ob__` is used nowhere else in the app. The initial bundle is 0.5 kB smaller than on `main`, because the rules are no longer scoped per component.

- **Exported documents are named in words, not in slug.** The save dialog offered `jetbrains_-_senior_software_developer_-_tailored_cv.pdf` for a document labelled "JetBrains - Senior Software Developer - Tailored CV": the old rule lower-cased everything, kept hyphens and turned spaces into underscores, so every separator came out as the unreadable `_-_`. The same document is now offered as **`JetBrains Senior Software Developer Tailored CV.pdf`** - the label's own words, single spaces between them, no hyphens and no underscores. Case is kept, because "JetBrains" is a name and "jetbrains" is not, and letters outside ASCII survive for the same reason: a company called Zürich no longer exports as `z_rich`. Characters a filesystem refuses are dropped rather than replaced, so removing one does not widen the gap between two words, and a name can no longer begin or end with a dot or a space - legal to write on macOS and Linux, silently trimmed by Windows. This is only the suggested name; the save dialog still lets you type anything.

### Fixed

- **Saving an edited CV no longer fails with `FOREIGN KEY constraint failed`.** `document_library.theme_id` is a real foreign key into `cv_themes`, and the CV editor always writes a theme - its picker defaults to Classic, id 1. On a database whose `cv_themes` row is missing, that made **every** CV save fail, permanently, with a raw SQLite error (`code: 787`) the user could do nothing about. `cv_templates` and `template_id` have the same shape. Both tables are pure lookup mirrors of constants that also live in `libs/core`, so a migration now puts the built-in rows back where they are absent; it is a no-op on a database that already has them. What emptied them in the first place is not established and is worth watching - this makes the app able to recover instead of bricking its own save path. Found on a real install whose `cv_themes` and `cv_templates` were both empty while both seed migrations were recorded as applied, with checksums matching their files byte for byte.

- **The Rust tests can now see a foreign-key violation at all.** `test_pool` never turned foreign keys on, and SQLite defaults them **off**, while the real pool is built with `.foreign_keys(true)`. Every constraint in the schema was therefore unenforced in tests - which is why the save bug above reached a user with the suite green. The new regression test builds its pool the way the app does.
- **"Open file" and "Show in folder" work on an exported document again.** Both commands hand a path to the OS launcher, so they are guarded - the point being that a bug or a compromised renderer must not be able to ask the backend to launch an arbitrary file. The guard admitted only files under the app's own data directory, which was true of the journal exports it was written for and is not true of the apply wizard's Export PDF: that writes wherever the save dialog pointed, usually Downloads. Applye therefore refused to open the file it had just written, with `refused: that file is outside Applye's own document folder` printed directly beneath the path it had just reported saving. A path now qualifies either by sitting under the data directory **or** by having been written by Applye during this run - provenance rather than location, so the threat model is kept rather than traded away. Only the extensions Applye actually exports (`pdf`, `docx`) are ever remembered, which keeps the launcher pointed at documents and never at something the OS would execute; the record is in memory only, so it is what this run wrote, not a growing list of everywhere the user has saved.
- **The job page's icon guardrail had been quietly narrowing with every split.** It reads the template, collects every `icons.*` reference and asserts the table defines them - but it only ever read `jobs.component.html`, and each component extracted from that page took its icon references somewhere the guard could not see. After this split the page was down to nine references and the guard's own "did the regex match anything" assertion fired, which is the only reason it surfaced. The templates are now discovered by asking which components read the table, so a child's `icons.doesNotExist` is caught in the fast gate as it always was for the page, and future splits stay covered without anyone remembering to come back. Coverage went from 9 icon references to 26.

### Changed

- **The wizard's export-and-apply step is its own component.** The jobs page is over budget in its template, its class and its stylesheet at once, and this step was 107 template lines of it. Everything it renders comes from services the page already provides component-scoped, so the new component injects them directly instead of taking them as inputs - which retires the four `DocumentExportService` aliases and the three one-line forwarding methods the page kept only so its template could name them. `Start over` stays on the page and is emitted, because it resets the tailoring, the score and the export state and then moves the wizard back to step 1. Template **786 -> 686**, class **1068 -> 1050**, stylesheet **624 -> 493**; all three are still over budget. No behaviour changed.

### Fixed

- **"Generating" no longer sticks forever on the CV card after you leave the job page and come back.** The CV draft asks two questions of the user through the gap dialog - once for what the job wants and the profile lacks, and again for any entry the model could not date. The dialog's service is scoped to the job page, so leaving the page destroys it while the generation carries on in the background, exactly as intended. The second ask then landed on that dead instance: it set "open" on signals no template was reading any more, so no dialog ever appeared, nobody could answer it, and the promise behind it never settled. The card sat on **Generating** with nothing on screen and nothing happening, and no error, because nothing had failed - the run was simply waiting for an answer it could never receive. A retired dialog now answers `null` instead of opening, which is what a cancel already does; gap-fill is optional on every path, so the CV is still produced. The cover letter was unaffected because it skips gap-fill entirely while a CV is generating.

- **Dependency-bump pull requests can pass CI again.** The attribution gate landed on 2026-07-31 and rejects any `Signed-off-by` trailer, but Dependabot signs every commit it opens, so every automated bump has failed the gate since - starting with the `ip-address` bump, whose lint, tests, build and file-size checks were all green. The gate exists to keep human and agent attribution off commits written by the maintainer; a bot signing its own dependency bump is not that. Commits are now skipped only when the author name carries the `[bot]` suffix a human GitHub account cannot have **and** the address is the matching GitHub noreply or support address. Either one alone is not enough, so setting a bot name locally does not buy an exemption, and the pull-request body is still inspected in every case.

### Fixed

- **Mark as Applied no longer leaves a second application row behind.** The action wrote its own `saved` row before committing the documents, and that row never reached the signal the job page holds, so the first commit step to ask for a draft found none and wrote a second row for the same job. The status then landed on one of the two and the other was orphaned. Creation now goes through the page's draft hook, which is the single owner of that row and of the signal. Confirmed in the running app: a job marked applied straight from its analysed state now ends up with exactly one row where it previously had two.

- **Mark as Applied says what it is doing.** Committing the documents generates whatever the application is missing, which runs against the configured AI provider and can take minutes. The button simply went dead for the whole time, with no spinner, no text and no toast, which reads as a hang. It now reads "Preparing documents…" while that step runs. `busy` alone could not say it, because saving a lead raises the same flag for an operation that takes a moment.

### Fixed

- **The rule that keeps discover off plaintext HTTP is now tested.** `require_https` is the only thing standing between a source row edited to `http://` and a request sent in the clear, and every fetch in the discover group passes through it - but nothing asserted it. Removing the check entirely left all 339 tests green. It now has a test covering plain HTTP, a missing scheme, an uppercase `HTTPS://` that does not match the check, and the `file:` and `data:` schemes a hand-edited row could otherwise smuggle in. No behaviour changed; the guard simply cannot be weakened silently any more.

### Fixed

- **An AI response that is valid JSON but not a CV no longer becomes an empty draft.** `parseCvSkillResponse` promised to throw on anything it could not read, so the caller could show what actually came back - but it only checked that `JSON.parse` succeeded. A model answering `"I could not read this CV"` in the JSON the prompt asked for parses fine as a string, and every field then fell back to `null`: the user got a blank editor with no reason for it, indistinguishable from a CV the model found nothing in. Numbers, `null` and bare strings are now treated as unparsed, which sends them through the repair pass and then to the error the function always documented. An empty object is still accepted, because a CV with no recognised fields is a real answer. Found by mutation testing during the split below: deleting the throw entirely left all 1195 tests green.

### Changed

- **The apply wizard's tailor step is its own component.** The three phase cards, the base-CV picker that starts a run, the in-flight line with its cancel, and the change and gap notes a finished run produced all come out of the jobs page, which is over budget in its template, its class and its stylesheet at once. The step injects `TailoringService` - which the page already provides component-scoped - rather than taking its state as inputs, which is what retires the seven declarations the page kept only so its template could name them. It deliberately starts nothing: tailoring, cancelling and re-tailoring each continue into page state the step knows nothing about (the export status, the post-tailor rescore, the linked documents), so the step emits and the page decides. Two things the split made testable rather than only moved: an empty base-CV select now provably reads as "tailor from the profile" rather than the document id 0 a bare `+''` produces, and the in-flight check is provably keyed by this job, so another job's run cannot animate this one. Nothing changes on screen. **Template 941 -> 786, class 1080 -> 1068, stylesheet 860 -> 624**, all three still over budget.

- **Reading an AI skill response is its own module.** `cv-content.util.ts` was 829 lines against a 400 budget and held the CV content model next to the code that reads what a model returned - two things that change on different occasions: one when a provider starts wrapping its answer a new way, the other when the CV gains a field. Fence stripping, the truncated-JSON repair, the skill and gap-response parsers and the date-answer parser move to `cv-parse.util.ts`. Their tests were already in a file called `cv-parse.util.spec.ts`, which had been testing a module that did not exist yet. **829 -> 622**, still over budget; the content model is the next cut. Consumers are unaffected: the new module is re-exported from `cv-content.util.ts` for the same reason `cv-style.util` and `cv-entry.util` are, since three of the importing files are themselves over budget and the size gate refuses to let them grow by an import line.

- **Discover's location rules separate from the vocabulary they match against, and three unenforced table rules became tests.** `discover-location.ts` was 910 lines against a 400 budget, of which about 780 were one list: every country, its names and ISO2 code, the cities worth resolving by name, and the US states and Canadian provinces. That list moves to `discover-location-tables.ts` and what stays is the matching itself - whole-word names, codes only as a standalone segment or an uppercase token, cities first, then states, then countries. **910 -> 128.** Three rules the table stated in comments and nothing checked now have tests: the region-generic entries ("Europe", "Asia") must stay last or they swallow the real country that follows, no city token may belong to two countries, and no ISO2 code may either - in each case the earlier entry wins silently and no caller can tell. The two documented collisions are asserted as behaviour rather than prose: `CA` resolves to California, not Canada, and `NL` to the Netherlands, not Newfoundland.

- **The file-size gate stops measuring one flat data table, and says exactly when that is allowed.** A vocabulary file is excluded only when it is a table and nothing else - no branching, no functions, every rule that reads it in another module - because its length then describes how many places a job board can name, not how it is built. The Discover location vocabulary joins the translation catalogue on that list, by exact path: `*-tables.ts` is not a category anyone can opt into. The exclusion has its own test asserting the opposite cases still fail - the rules module beside it, the table's own spec file, and a same-named file anywhere else - because an exclusion that leaks stops measuring the code it exists to keep measurable.

- **Discover's geography splits into scopes and countries, and a silent way to widen a market scan is now tested.** `discover_geo.rs` was 522 lines of source against the 500 budget, holding two things that grow on different occasions: the region scopes, a short list of continent buckets, and the per-country vocabulary - every city, state and spelling a two-letter code also answers to - which grows whenever a market is added or a board starts naming places a new way. The long half moves to `discover_geo_countries.rs`. While splitting, a real coverage gap surfaced: removing `gb` from `KNOWN_COUNTRY_CODES` left all 344 tests green, yet it changes what a scan returns. The "somewhere else" set skips a whole region whose list overlaps the selected market, so for a Germany market the European names come only from each country's own entry - without `gb`, "Remote - London" stops reading as somewhere else and passes a Germany scan on the word "Remote". That list now has a test, as does the deliberate `ca` collision, where Canada gives up its own bare ISO code because in a job location it means California far more often. **522 -> 246**, with 293 in the new module.

- **The from-link flow stopped owning the helpers four other modules were importing from it.** `job_url.rs` was 580 lines of source against the 500 budget, and the excess was code that has nothing to do with classifying a pasted link: turning markup into plain text, reading a value out of an XML tag, and pulling the host, the path segments and a display name out of a URL. Four discover modules already imported those from `job_url`, which is the wrong module to name for a helper that knows nothing about the paste flow. They now live where consumers can name them honestly - `web_text.rs` for `strip_html` and `xml_tag`, `url_parts.rs` for `extract_host`, `path_segments` and `titleize_slug` - with the markup tests moving alongside the code they cover. What stays in `job_url.rs` is the host allowlist and the six per-board readers. `extract_host` gained the tests it never had, which matters because it produces the exact string the allowlist matches a closed board against. **580 -> 399, under budget.**

- **The ATS check's vocabulary is its own module.** `ats.rs` was 619 lines of source against the 500 budget, and most of the excess was one table: the English and German stopword list. That list, the tokenizer that keeps `c++`, `.net`, `node.js` and `ci/cd` intact, and the two rules deciding whether a term looks technical rather than prosaic all move to `ats_tokens.rs`. What stays is the scoring. `ats_format.rs` had been importing `tokenize` back out of `ats.rs`; it now names the module that defines it. **619 -> 289, under budget.**

One press of Parse & filter now carries the whole chain: the deterministic rules first at 0 tokens, then - only when they missed - a single `job-identify` call on the economy model, then a dialog asking the user. The AI step is deliberately not behind its own button, because it runs exactly when a button would have been worth pressing, and three presses on every badly formatted posting is worse than one. The posting that defined the problem has its role in prose ("Our partner is looking for an AI-Native Software Developer") and no employer at all: it is listed by a matching platform on behalf of an unnamed partner. **Naming that platform is the canonical wrong answer** - it produces a cover letter opening "I am excited to apply to Jobgether", confidently and in the user's name - so the prompt's load-bearing rules say the company is the employer and not the board, the agency or the platform, and that a posting listed on behalf of an unnamed partner has no company. Skip is remembered on the job row rather than in the browser, because it is a fact about the job - and it silences the dialog only, not the AI, since "stop asking me" and "stop reading the posting" are different instructions; a quiet "Name it yourself" stays on the card, so skipping closes the interruption without closing the road back. What the AI named is marked `inferred` and shown with a label, never as a quotation from the posting. What the user typed is marked `user` and is **never overwritten by a re-parse** - without that, a hand-typed company goes through `is_usable_company` on the next parse and is thrown away for not looking like a company name, a validator built to reject stale garbage being unable to tell it from an employer with an unusual name. **Identification does not run inside the parse.** The parse is over when the row is written: deterministic, 0 tokens, milliseconds. Identification is a second phase - an AI round-trip bounded only by a network, then a dialog bounded by nothing but the user - and the first cut of this held Parse & filter disabled across both, which is a spinner reporting a parse that already finished and a wait that may never end. `ai_run` allows ten minutes, right for a tailoring pass and absurd for two short strings, so the phase also has its own 45-second bound. The dialog is raised by whoever is rendering the job rather than by the service, so being on screen is what proves the user is still looking. The two numbers collide silently whenever both tables have a row at that number, which is most of the time, so this was not an edge case but the normal path. The sibling link is the control case and is untouched: `/interview-prep/:id` really is keyed by application, so the same `card().id` that was wrong above is right there, and a test now pins both. `job_id` is nullable in the schema, so a card with no job attached is a no-op rather than a navigation to `/jobs/undefined`. The regression test was checked against the old code first, so it is known to catch the bug rather than merely to pass.

- **The follow-up draft's double-click guard never worked.** Found by the extraction below, not reported: `draft()` set its `drafting` flag _after_ `await getSettings()`, so a second click landing during that read sailed past the guard and started a second billed AI call that also wrote the cache. The flag is now claimed before the first await. Fixed rather than recorded, because the alternative was committing a test that asserts the broken behaviour.

- **A second gap dialog could strand the first document on "Generating" forever.** Reported from the app: starting a cover letter while a CV was still generating raised a second "fill the gaps" dialog for the same questions, and afterwards one of the two documents never finished. Two defects in one flow. Both document flows awaited a single `gapResolver` field, so a second caller overwrote it and the first caller's promise never settled - its `await` never returned, its `finally` never ran, and the in-flight marker for its document was never cleared. Ownership is now an explicit rule instead of whoever wrote to the field last: first caller wins, a second is answered `null` immediately, which is exactly what a cancel yields and what every caller already tolerates. The duplicate dialog was a separate miss: the cover-letter flow skips gap analysis when a CV is _linked_, but a CV that is still generating has not linked itself yet, so a cover letter started alongside one ran a second analysis. It now also skips while a CV is preparing, which is the condition the comment always claimed. The fix arrived as an extraction because the new file-size ratchet refused the in-place version - and that was the right call, because the invariant now has a home and the test seam it never had: `CvGapDialogService`, 14 tests, the collision covered directly.

- **Onboarding sent an empty model to DeepSeek, and there was no way to pick one.** Choosing DeepSeek on the AI step and saving a key still failed every call in the wizard with `The supported API model names are deepseek-v4-pro or deepseek-v4-flash, but you passed .` - reported by a user as a resume that would not parse, which is what the screen said. The step persisted `aiMode` and `provider` but never the model ids, and the dispatcher read the model back out of the settings row, so the wizard sent whatever was stored there: `claude-haiku-4-5` on a fresh install, which DeepSeek rejects, or the empty string a previous CLI-mode run deliberately leaves behind. The same class of bug had already been fixed once for the provider itself, and the lesson did not carry: for the duration of the wizard the settings row is not the truth. Settings had all the machinery to prevent this - a model catalogue, per-provider defaults, and a reconciler that repairs a blank or foreign id - but it was private to that screen, so onboarding could not use it and was free to disagree with it. It now lives in `@applye/core` as `api-models`, both screens read from it, and the wizard gained quality and economy model selects seeded from stored settings and reconciled on every provider or mode change. CLI mode still blanks the pair on purpose: a CLI rejects API model ids and picks its own default. One subtler fix came with it - the settings read is async while the step is interactive from the first frame, so a fast click now wins over the seed instead of being silently overwritten by it.

- **A spec was asserting the opposite of what the score gauge does.** `score-gauge.spec.ts` set a score in `beforeEach` and then changed it inside each band test. A change after mount is the _animating_ path - the gauge tweens over 700 ms of `requestAnimationFrame` and the colour band follows the animated value - so every band assertion was a race against that tween. It passed only because the library suites ran under zone.js, which patches `requestAnimationFrame`, while both applications run zoneless. Moving the libraries to the zoneless test environment surfaced it immediately: two tests failed because the band had not moved yet, which is exactly what a user sees. The band tests now set their score before the first effect run, which is the snapping path, so they test threshold logic and nothing else. Two tests were added rather than removed: one pins that the gauge snaps on mount instead of counting up from zero, and one covers the tween honestly by driving real animation frames until the value settles - behaviour that had no coverage at all, since the only tests touching it were asserting its opposite.

- **A dead store in the tracker print view.** `tracker-report-print.component.ts` initialised `all` to `[]` and then assigned it in both branches of the `try`/`catch` that follows, so the initialiser could never be read. Harmless, and found only because ESLint 10 promotes `no-useless-assignment` into `eslint:recommended` - which is a small argument for taking these bumps rather than deferring them indefinitely.
- **The release matrix could not build anything.** All four jobs for `v0.29.1` failed within seconds of `'nx' is not recognized as an internal or external command`. `tauri-action` invokes `tauri build` directly rather than through an npm script, and only npm puts `node_modules/.bin` on `PATH`; locally the command works because `desktop:build:tauri` wraps it, so nothing local could reproduce it. Both `beforeDevCommand` and `beforeBuildCommand` are `npx`-prefixed now.
- **The CSP guard was absent from the one path that ships bytes to users.** It runs inside the npm script and as a `ci.yml` step, and `tauri-action` goes through neither - so the release build, the only build a user ever downloads, was the only build without the check that exists precisely because a release went out unstyled. ### Removed

- **NgRx is gone, and the reason is not the one usually given.** `@ngrx/signals` was a single `signalStore` in `libs/data`, seventy-six lines holding six externally-used members, five more that nothing called, and a peer range pinning `@angular/core` to one major. It has been replaced by a plain `@Injectable` using `signal()` and `update()` - the same behaviour, the same public surface for the two components that consume it, no library. The bundle argument, which is the one usually reached for, does not hold up: tree-shaken it was a small slice of a 2.2 MB bundle and removing it saves almost nothing. The argument that does hold is coupling. NgRx's peer range would have gated _every_ future Angular major on a release of a dependency doing seventy-six lines of work, and it was already gating this one. `libs/data` also stops re-exporting `Job` and `JobOverview`, which had it republishing the domain layer's API through the data layer's entry point.
- The store's dead members went with it: `selected`, `selectedId`, `count`, `mutating` and `loadJob` were unreferenced across every `.ts` and `.html` in the workspace.

- **`zone.js` is gone, and it turns out it was never shipping in the first place.** Both applications have run zoneless for some time, and with the library test suites moved across nothing in the repository loads it. No project configuration has a `polyfills` entry, so the dependency was never bundled - its only remaining effect was to patch `requestAnimationFrame` inside three test environments, where it made a spec pass by asserting behaviour production does not have. It is an optional peer of `@angular/core`, so removing it is not a peer break. Confirmed at runtime rather than inferred: with the dependency gone the dev server boots, the app renders, and `window.Zone` is `undefined`.

- **`@angular/animations` is gone because nothing imported it.** No `@angular/animations` import, no `provideAnimations`, no `BrowserAnimationsModule`, no `animate()` anywhere in `apps/` or `libs/`. It was also the one genuinely inconsistent entry in the dependency tree: `npm ls` reported `@angular/core@21.2.19 invalid`, because `@angular/animations` had resolved to 21.2.17 and pins `@angular/core` to exactly 21.2.17. Removing the package resolves that, rather than papering over it by bumping something nothing imports.

### Security

- **Five quadratic regexes in `libs/core` no longer run on pasted text.** CodeQL flagged all five as `js/polynomial-redos`, high severity, and it was right: they parse job descriptions, CVs and model output, so their input is uncontrolled by definition. Measured on a 40 000-character pathological string, each took between 0.6 s and 1.5 s, and cost grows with the square of the length - roughly six seconds at 100 000 characters, on the UI thread, from nothing more exotic than a paste. The salary parser's percentage strip and the signature sanitiser's email pattern get bounded repetition counts (twelve digits, and the RFC 5321 lengths); a bounded email still takes the `@` and the domain with it, so no usable address survives a partial strip. The scoring-JSON fence loses a leading `\s*` that the following `.trim()` already covered. The two "trailing `(...)`" parsers behind the education and language editors drop their regex for a string scan that cannot backtrack, keeping the old behaviour on unbalanced input, which is now pinned by tests. Each of the five has a regression test that asserts a wall-clock bound on a 100 000-character input, because the failure mode is a hang rather than a wrong answer.

- **Twelve of the seventeen open dependency advisories are closed by pinning transitive versions, and the remaining five are explained rather than left silent.** None of the seventeen ever shipped: `npm audit --omit=dev` was at zero before this change and is at zero after, and the one alert with runtime scope is a Rust crate, not npm. What the advisories were doing was hiding a real one - the reason to clear them is the same reason `.cargo/audit.toml` exists, so that a _new_ finding is visible instead of lost in known noise. `axios`, `postcss`, `webpack-dev-server`, `body-parser`, `js-yaml` and `brace-expansion` are pinned through `overrides` to the patched release inside their own major. Two details were worth getting right: npm's advisory database and Dependabot's named _different_ vulnerable ranges for the same packages, so the copies that actually needed pinning were `js-yaml` 3.14.2 and `brace-expansion` 5.0.6 rather than the majors the alerts pointed at; and several advisories were backported to each release line separately, so the overrides use `@major` selectors instead of dragging a `minimatch` 3.x consumer across a major boundary. `uuid` 8.3.2 -> 11.1.1 and `@hono/node-server` 1.19.14 -> 2.0.5 follow, each a major, each taken only after the consumer was identified and the result verified: `uuid` is reached through `sockjs` under `webpack-dev-server`, which Angular 21 does not even use at dev time any more (its dev server is Vite), and `@hono/node-server` is reached through the Angular CLI's MCP server, which nothing in this repository invokes. The dev server was started and the app rendered with no console or server errors, because a passing unit-test suite is not evidence about a dev-server dependency. **Of the seventeen alerts, sixteen are now closed.** The seventeenth is `glib` and is not fixable here.

- **A clean `npm audit` was available and was refused, because it would have been a lie.** One advisory is left - `brace-expansion` GHSA-mh99-v99m-4gvg, patched only in 5.0.8 with no backport to the 1.x or 2.x lines. Forcing every copy to 5.x takes the full `npm audit` count to **zero**, and it was tried. It also breaks `minimatch` 3.1.5, which `test-exclude` and `fork-ts-checker-webpack-plugin` still carry: `brace-expansion` 5's CJS entry exports `{ EXPANSION_MAX, EXPANSION_MAX_LENGTH, expand }` instead of a bare function, and `minimatch` 3.1.5 does `var expand = require('brace-expansion')` and calls it, so both copies throw `expand is not a function` on load. Nothing in the repository catches that: with the override in place `npm audit` read 0, the entire gate went green, and even `nx test core --coverage` passed, because Jest 30 resolves its own newer `minimatch`. A pin that reads as a clean sweep would have left two live landmines behind, so the override is reverted and the advisory is recorded in `docs/governance/VALIDATION_MATRIX.md` with the exact failure and its drop condition. The full `npm audit` count lands at 23, all of it path nodes of that one advisory.

- **The `glib` advisory is Linux-only, unreachable, and not fixable here - recorded so it stops being re-triaged.** RUSTSEC-2024-0429 is unsoundness in `glib::VariantStrIter`. It is the only dependency alert with runtime scope, so it is the only one that could ship. `glib` sits at 0.18.5 because the whole gtk-rs 0.18 stack (`atk`, `cairo-rs`, `gdk`, `gio`, `gdk-pixbuf`, `gdkx11`) reaches it through `gtk` 0.18.2, which is what `tauri` 2.11.5, `wry`, `tao` and `muda` pin; `cargo update -p glib` moves nothing. Applye's Rust code never calls `glib` directly, the whole stack is `cfg(target_os = "linux")`, and `cargo audit` already reports it as an allowed unsound warning at exit 0. **Drop when:** Tauri's Linux backend moves off gtk-rs 0.18.

- **Your profile now stores a first name and a last name, not just the full name.** Generated documents and future job-board autofill need the parts, not just the whole - so your profile now keeps both alongside the display name you already had. When a resume parse cannot tell where the name splits, the onboarding review step asks you to check it, without blocking you from moving on. If you saved your profile before this change, the first and last name are filled in from your display name the next time you open it.

### Fixed

- **Onboarding now remembers which AI provider you picked.** It saved your API key but never the choice itself, so picking OpenAI or DeepSeek and pasting that key still left the app set to Claude - and every task failed with "no key stored for claude". The provider and the mode are now saved when you finish the wizard.
- **Switching AI mode no longer leaves you with an unusable model setting.** Going to CLI mode clears the model boxes on purpose (so the CLI picks its own), but switching back to API mode left them empty and every request was rejected. Coming back now restores your provider's models.
- **The health check tells the truth in CLI bridge mode.** It reported "no stored key needed - OK" without ever checking whether the CLI it would call actually works, so a missing or broken CLI still showed a clean bill of health. It now runs the CLI and reports the version, or fails with the reason.
- **Settings no longer claims a broken CLI is ready to use.** The CLI bridge checked only that a command with the right name existed, so a half-finished install showed a green tick and then failed on the first real task. These CLIs are small wrappers around a platform binary, and an interrupted install leaves the wrapper behind with the binary missing. Applye now actually runs the CLI to check it, and shows one of three things: working (with its version), **found but broken** (with the exact reinstall command and the error it printed), or not installed. "Send a test prompt" is only enabled for a CLI that genuinely runs.
- **You can now pick a CLI model from a list instead of typing its name.** CLI mode used free-text model fields, which assumed you knew what your CLI calls its models - and a leftover name from API mode could be sent to a CLI that does not recognise it. Each CLI now offers a dropdown: **CLI default**, which is the recommended choice and simply lets the signed-in CLI pick whatever your subscription covers; the model names that CLI accepts; and **Other**, which reveals a text field for anything not listed. Claude Code offers `sonnet` / `opus` / `haiku` and Codex its `gpt-5.x` names; Gemini CLI publishes no list that can be read without signing in, so it offers the default and a text field rather than names that might be wrong.
- **The bottom of long pages keeps its breathing room.** Scrolling to the very end of a page (your Profile, for one) could leave the last card pressed against the window edge; every scrolling page now keeps a consistent gap at the bottom.
- **The welcome screen fits a window that is not maximised.** Its spacing was fixed rather than proportional, so on a half-height window the very first screen you ever see arrived with a scrollbar and the health check pushed off the bottom. The layout now scales with the window: a large screen looks exactly as before, a smaller one tightens up instead of scrolling.

- **Dashboard attention cards read more clearly.** The needs-attention cards used a thin colored stripe down one edge; they now use a full colored border with a subtle tint, easier to read and consistent with the rest of the interface.
- **Consistent dashes across the interface.** Every user-facing string and separator now uses a plain hyphen, in line with the project's typography rule.

### Added

- **CLI bridge mode works.** Settings has offered a "CLI bridge (coming soon)" mode since the first AI release, but choosing it returned "not implemented yet". It is now real: if you already pay for **Claude Code**, **Codex CLI** or **Gemini CLI**, Applye runs that CLI for its AI work and stores no API key at all. Settings shows which of the three it can find on your machine, with the path it resolved, and a Re-check button - a GUI app does not inherit your shell's `PATH`, so Applye also looks in the standard install locations itself. Each run is a one-shot subprocess with a fixed argument list (never a shell), the prompt goes in over stdin rather than the command line, the working directory is a scratch folder rather than your own files, Codex additionally runs in its read-only sandbox, and a CLI that hangs is stopped after 10 minutes. Model names in CLI mode are free text passed straight through; leave them empty and the CLI picks its own default.

### Changed

- **The ATS check is now a measurement, not an opinion.** It used to be a single true/false the scoring model emitted alongside a one-line note - so it read as a number while actually being a guess, it never looked at the CV that would be uploaded, and it could disagree with itself on identical input. It is now computed locally in Rust at zero token cost, and gives the same answer every time. The result is a **0-100 score** built from two halves: **keyword coverage** (60 points) matches the posting's own requirement terms against your tailored CV, weighting terms inside a requirements block double because that is where a recruiter's filter comes from, and matching whole words so "Java" no longer counts as covered by "JavaScript"; and **parsability** (40 points), which flags the things that actually lose information in a parser - no findable email or phone, table layouts, missing section headings or creative ones a parser will not recognise, no years to compute tenure from, an export that came out suspiciously short, and a photo **only in markets where a photo is a liability** (a Bewerbungsfoto is normal in DE/AT/CH and is not flagged there). Every finding is shown with the reason attached, and the missing keywords are listed so you can decide rather than trust a number. Requirement headings are recognised in English and German. The model's own ATS remark is still shown, now clearly below the computed result as advice.
- **Date ranges in exported documents use a plain hyphen.** A CV or cover letter exported from Applye wrote its date ranges with an en dash ("2020 - 2023" was actually "2020 - 2023"). Some applicant tracking systems and older parsers mis-read that character, and it was inconsistent with the rest of the app. Exports now use a plain hyphen throughout. Documents you exported earlier are unaffected until you export them again.
- **The first launch now welcomes you.** The first time you open Applye it greets you with an animated screen: the logo, a one-line summary of what the app does, and two clear choices - take a short guided setup, or skip it and fill things in yourself. The 0-token health check stays on the same screen so you can confirm everything is set up. Skipping never blocks you, and the empty-profile hint still nudges you from inside the app. The animation stands down when your system asks for reduced motion.
- **The top-bar buttons use the shared button styles.** The theme toggle and Paste Job button had their own one-off styling; they now use the same design-system buttons as the rest of the app, so sizing, focus rings and hover states match everywhere.

A board that is itself national vouches for its own postings, because those feeds routinely carry no location field at all.
- **Seven new built-in Discover sources**, all shipped disabled like every other built-in - no request reaches any of them until you turn one on. Four cost zero new parser code, being standard RSS: **DOU.ua** and **Djinni.co** (Ukraine), **Habr Career** (Russia), **Jobicy** (a remote-first board weighted toward the US). Three needed a new JSON parser each, all probed live before being added: **TrudVsem** (opendata.trudvsem.ru, the Russian federal labor service's open-data API, 540k+ postings), **Arbeitnow** (a German-market board), and **No Fluff Jobs** (a Polish IT board). Every endpoint above is public and needs no key.

### Fixed

- **No Fluff Jobs postings now show their full content in Discover** - required skills, nice-to-have skills, the requirements text, the day-to-day responsibilities and the salary - instead of a three-word category/technology/seniority summary. No Fluff Jobs' list endpoint carries no description, so the scan now fetches each posting's detail page (`GET /api/posting/{slug}`), the same pattern already used for the German federal agency (Arbeitsagentur), under the same shared per-scan detail budget. Every other Discover source already stored a real description, so this was a No Fluff Jobs-specific gap, not a general one. Because the old three-word stub was the only text the detail description, the salary line, skill detection and the raw keyword score all read from, fixing it restores all four at once. Złoty (PLN) salaries are also now detected - the salary extractor previously recognised only euro, pound, dollar, EUR, USD and GBP, and silently missed every PLN posting.
- **Region-mode "Europe" no longer drops Ukrainian jobs.** Ukraine was missing from the list of European countries the region filter matches against, so picking the Europe region silently excluded every Ukrainian posting. Ukraine is on that list now. This is a plain filtering fix, independent of the local markets work above.
- **With a local market selected, a job with no location at all is now dropped instead of shown.** A worldwide source occasionally carries a job with no location field whatsoever, and with no location there is nothing to tie it to your market, so it is filtered out. Sources for the market itself are exempt from this, because their feeds often omit the field entirely and a national board already vouches for its own postings.
- **An AI request could hang forever with no error and no way out.** Every API-mode call used an HTTP client with **no timeout of any kind**, so a connection that was accepted and then went quiet - a dropped wifi link, a laptop that slept mid-request, a stalled provider - was waited on indefinitely. Nothing downstream could recover: the request never returned, so the screen that was waiting on it sat on "Generating…" or "Scoring…" permanently, with no error to explain it and nothing to retry. This affected every AI feature in API mode (CV tailoring, cover letters, scoring, interview prep), and it is what made Interview Prep's generation appear to hang. Requests now have a bounded budget: 15 seconds to connect, so an unreachable provider is reported in seconds rather than never, and 10 minutes overall to match what CLI bridge mode already enforced - long enough for a genuinely slow answer, finite either way. The same missing timeout was found and fixed in **paste-from-link**, where a stalled job board could hang the import the same way.
- **Buttons that sat alone in a Settings card stretched across its full width.** "Re-run onboarding" was the visible case. The card is a stretch-aligned column, so any button dropped straight into one filled it; "Send a test prompt" only looked right because it carried a one-off override. Fixed for every such button at once, so a new one cannot inherit the bug.
- **Built-in sources could silently fail to install if you had added your own sources first.** Every built-in-source migration (including Bundesagentur fuer Arbeit, added earlier) hardcoded a low row id and depended on it being free. `sources.id` is an ordinary autoincrementing column that your own added sources use too, so on an install with a few of those already, a new built-in's id could already be taken - the insert then silently did nothing instead of adding the source, with no error anywhere. Found live against a real database with four custom sources: Bundesagentur fuer Arbeit had never actually been installed despite shipping weeks ago, and the same bug was about to repeat for four of the seven local-market sources above. New built-in sources are now inserted without a fixed id (same as one you add yourself gets) and de-duplicated by URL instead, so this can't recur. Existing installs get Bundesagentur fuer Arbeit and any local-market sources that were silently skipped backfilled automatically on next launch - nothing to do on your end.
